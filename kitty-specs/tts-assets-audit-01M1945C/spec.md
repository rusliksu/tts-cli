# Спецификация: аудит ресурсов TTS-сейва

**Ветка**: `codex/tts-assets-audit`
**Создано**: 2026-08-30
**Статус**: WP01-WP02 завершены; baseline WP03 одобрен к реализации
**Основание**: локальный read-only пилот `tts assets audit` для произвольных JSON-сейвов Tabletop Simulator.

## Пользовательские сценарии и проверка

### Сценарий 1 — Проверить локальную полноту мода (P1)

Пользователь передаёт один JSON-сейв Tabletop Simulator и получает перечень
уникальных структурированных ресурсов с доказуемым статусом присутствия в
локальном кэше.

**Почему P1**: это минимальная самостоятельная ценность пилота и основа всех
последующих backup, network-check и repair сценариев.

**Независимая проверка**: запустить CLI на синтетическом сейве с известным
набором кэшированных и отсутствующих ресурсов и сравнить полный результат.

**Приёмочные сценарии**:

1. **Дано** изображение, чей канонический ключ присутствует в кэше, **когда** выполняется аудит, **тогда** ресурс получает `cached` и путь найденного файла.
2. **Дано** поддерживаемое структурированное поле URL без совпадения в кэше, **когда** выполняется аудит, **тогда** ресурс получает `not_found_in_cache`, но не объявляется сетево недоступным.
3. **Дано** несколько объектов с одним URL, **когда** выполняется аудит, **тогда** в отчёте один ресурс со всеми отсортированными JSON-путями использования.

### Сценарий 2 — Передать отчёт AI-агенту или скрипту (P1)

Пользователь запрашивает JSON и получает стабильную схему, детерминированный
порядок данных и документированный exit code.

**Почему P1**: агентное использование — ключевое отличие от существующих GUI и
TUI менеджеров модов.

**Независимая проверка**: два последовательных запуска на неизменных входах
возвращают байт-в-байт одинаковый stdout и одинаковый exit code.

**Приёмочные сценарии**:

1. **Дано** неизменное содержимое сейва и кэша, **когда** команда с `--json` запускается дважды, **тогда** stdout совпадает полностью и не содержит времени выполнения.
2. **Дано** хотя бы одно неподтверждённое локальное совпадение, **когда** аудит завершён, **тогда** exit code равен `1`, а JSON остаётся валидным полным отчётом.

### Сценарий 3 — Получить короткую сводку для человека (P2)

Без `--json` пользователь видит имя сейва и компактные счётчики объектов,
Lua-скриптов, ресурсов, типов и статусов.

**Почему P2**: удобно для ручного запуска, но не требуется для машинного
контракта.

**Независимая проверка**: счётчики human-вывода сравниваются со сводкой того же
аудита в JSON.

**Приёмочный сценарий**:

1. **Дано** корректный сейв, **когда** команда запускается без `--json`, **тогда** сводка содержит те же итоговые счётчики, что и JSON-отчёт.

### Сценарий 4 — Установить проверенный релиз из PyPI (P1)

Пользователь устанавливает `tts-cli==0.1.0` из production PyPI и получает тот
же CLI, который опубликован GitHub-тегом `v0.1.0`.

**Почему P1**: установка из package index устраняет необходимость клонировать
репозиторий и делает CLI пригодным для агентов и автоматизации.

**Независимая проверка**: установить wheel из PyPI в чистое окружение, запустить
`tts --help` и выполнить аудит синтетического сейва.

**Приёмочные сценарии**:

1. **Дано** GitHub-тег `v0.1.0`, **когда** publish workflow собирает пакет, **тогда** тег и checkout указывают на `54af70be429ea0aa49922b9984af3e099e66cd54`, версия в `pyproject.toml` равна `0.1.0`, а wheel и sdist проходят `twine check --strict`.
2. **Дано** привязанный PyPI Trusted Publisher, **когда** разрешённый workflow запускается для `v0.1.0`, **тогда** пакет публикуется через OIDC без API-токена.
3. **Дано** опубликованный `tts-cli==0.1.0`, **когда** пакет ставится из production PyPI в чистое окружение, **тогда** console script `tts` доступен и выполняет read-only аудит.

### Граничные случаи

- Повреждённый JSON, отсутствующий файл или неверный каталог кэша завершаются с кодом `2` и короткой ошибкой в stderr.
- Пустой корректный сейв даёт нулевые счётчики и код `0`.
- Рекурсия охватывает словари и массивы, включая `ObjectStates`, `ContainedObjects` и значения `States`.
- HTTP(S) URL в неизвестном поле с суффиксом `url` остаётся `unverified`; произвольный текст и Lua-код в пилоте не сканируются.
- Старый `cloud-*.steamusercontent.com` и новый `steamusercontent-a.akamaihd.net` сопоставляются по стабильной UGC-паре, а не по hostname.
- Локальные `file://` и абсолютные пути не считаются внешними URL пилота.
- Если сейв находится в `Saves`, каталог `Mods` обнаруживается как соседний каталог общего TTS-корня.
- Несколько cache-кандидатов для одного URL дают `unverified`, а не произвольный `cached`.

### Основные сущности

- **AuditReport**: версия схемы, сведения о сейве, сводка и отсортированный список ресурсов.
- **AssetReference**: исходный URL, набор типов и usages с JSON Pointer, полем и inferred type.
- **CacheMatch**: статус, локальный POSIX-относительный путь или `null`, метод, confidence и число кандидатов.
- **AuditSummary**: счётчики объектов, Lua-скриптов, ресурсов, типов и статусов.

## Критерии успеха

- **SC-001**: все синтетические тесты проходят на Python 3.12+.
- **SC-002**: два JSON-запуска на одном fixture совпадают байт-в-байт.
- **SC-003**: локальные read-only проверки завершаются на Avalon, Clank! Catacombs и EPIC Terraforming Mars без изменения исходных файлов.
- **SC-004**: EPIC-аудит завершается менее чем за 10 секунд.
- **SC-005**: privacy scan всего набора tracked-файлов не находит реальных Workshop IDs, Steam asset URL или абсолютных пользовательских путей.
- **SC-006**: golden tests покрывают пустой отчёт, смешанные usages одного URL, неоднозначный cache match и все exit codes `0/1/2/3`.
- **SC-007**: публичный `main` соответствует проверенному task head, CI зелёный, visibility равна `PUBLIC`, license определяется как MIT.
- **SC-008**: PyPI JSON API возвращает `tts-cli` версии `0.1.0`, а установка из production index в чистое окружение проходит smoke.
